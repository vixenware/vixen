## Body

## Summary

Support compilation profiles that control optimization level, debug info, overflow checks, LTO, and other codegen settings.

## Current state

The codebase has a `Profile` enum (debug/release) that flows into cache keys, but the full profile configuration story is undefined.

## Scope

### Built-in profiles

- **debug**: opt-level=0, debuginfo=2, overflow-checks=on (fast compile, good debugging)
- **release**: opt-level=3, debuginfo=0, overflow-checks=off, LTO as configured
- Match Cargo's defaults so existing expectations transfer

### Custom profiles

Cargo supports `[profile.bench]`, `[profile.test]`, and `[profile.custom-name]` with inheritance. Do we want this?

### Profile settings

At minimum:
- `opt-level` (0, 1, 2, 3, s, z)
- `debug` (debuginfo level: 0, 1, 2, "line-tables-only")
- `overflow-checks` (bool)
- `lto` (off, thin, fat)
- `codegen-units` (1 for determinism, N for parallelism)
- `panic` (unwind vs abort)
- `strip` (none, debuginfo, symbols)
- `incremental` (always off for vixen — we have our own caching)

### CLI

- `vx build` → debug profile
- `vx build --release` → release profile
- `vx build --profile custom-name` → custom profile

### Cache interaction

Profile is already part of the cache key. Different profiles produce different artifacts in different output paths.

## Open question: where are profiles configured?

- In Cargo.toml's `[profile.*]` sections? (Cargo compat)
- In a vx-specific config file (vx.styx, vx.mag)?
- Both? (Read Cargo.toml profiles but allow override in vx config)

See also #150 (rule language exploration) — profile definitions could live in the rule language.
