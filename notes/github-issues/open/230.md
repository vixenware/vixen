## Body

## Summary

Define the **multi-level build authoring model** for vixen, so users can choose their abstraction level:

1. **Zero-config / drop-in Cargo replacement**
2. **Static document configuration** (e.g. `vx.styx`, and potentially other declarative formats)
3. **Full Vixen language rules** for advanced/custom orchestration

This issue describes the intended dual nature of the system: easy defaults for common Rust workflows, and full programmable control for unusual or multi-language builds.

## Problem

Current discussions split into:

- built-in Rust rule parity
- language/runtime/tooling for Vixen language

But we need a clear product-level contract for how these modes coexist, compose, and transition.

Without this, we risk:

- unclear UX boundaries
- duplicated configuration surfaces
- hidden policy in kernel APIs
- unclear migration path from simple to advanced usage

## Vision

vixen should support an **abstraction ladder**:

1. **No config**
- `vx build` on a Cargo workspace should "just work"
- built-in rule pack handles toolchain acquisition, build scripts, proc macros, etc.

2. **Static config documents**
- users can express policy/preferences declaratively (targets, toolchain pins, profiles, layout, cache policy, etc.)
- still mostly data, low cognitive load

3. **Vixen language rules**
- users can define custom planning logic for special workflows
- including multi-language pipelines and bespoke dynamic behavior

Users can stop at any layer, or move up layers incrementally.

## Key Design Principle

**Policy belongs in rule/config layers; mechanism belongs in the kernel.**

- Kernel exposes deterministic primitives and execution/storage infrastructure.
- Built-in rules implement the default behavior.
- Static configs feed rule inputs.
- Advanced users can override/extend behavior with Vixen language.

## Proposed Architecture Contract

### 1) Inputs as typed facts

All entry points (Cargo metadata, `vx.styx`, optional JSON/other sources, CLI flags, env allowlist) are normalized into typed planner facts.

Example fact kinds:

- `:build/request`
- `:project/config`
- `:workspace/metadata`
- `:toolchain/preference`

### 2) Built-in rule packs consume the same facts

Default Rust behavior should be a rule pack consuming those facts (not hardcoded planner branches).

### 3) User rule packs can extend/override at defined seams

Define explicit extension points (e.g. pre-unit expansion, post-build-script discovery, link strategy selection) with deterministic merge/precedence rules.

### 4) Deterministic fallback chain

If user provides no custom rules, built-in rules run.
If user provides static config only, built-in rules honor config-derived facts.
If user provides custom rules, they are composed by explicit precedence (to be specified).

## Questions to Resolve

- Which static formats are first-class vs adapter-based?
- Do we support both "replace" and "augment" semantics for custom rules?
- How is precedence declared and audited?
- What diagnostics explain which layer made a planning decision?
- How do we keep "drop-in cargo replacement" fast while supporting advanced mode?

## Acceptance Criteria

- Product/design doc defines the three abstraction levels and their guarantees.
- Input normalization model (documents/CLI/etc. -> facts) is specified.
- Extension/override seams are documented with precedence rules.
- Explain output includes layer provenance (built-in rule vs static config vs custom rule).
- Migration guidance exists for moving from no-config -> static config -> custom rules.
