# Issue #191: Stream extraction: extract tarballs while downloading instead of after

## Body

## Problem

Toolchain acquisition currently downloads the entire tarball to memory/disk, then extracts it. These are sequential: download finishes, extraction begins. For a 61 MB rustc tarball or 170 MB rust-std, this adds seconds of dead time.

## Fix

Tarballs (tar.gz, tar.xz, tar.zst) are streaming formats — you can decompress and extract entries as bytes arrive from the network. The download and extraction should be pipelined:

```
Network → Decompressor → Tar reader → CAS ingestion
```

All in one streaming pipeline. No intermediate full-tarball buffer.

## How it works

- HTTP response body is an `AsyncRead` / `Stream<Bytes>`
- Pipe into async decompressor (gzip/xz/zstd)
- Pipe into tar entry reader
- As each entry is complete, ingest into CAS immediately
- The first files are available in CAS before the download finishes

## Benefits

- Toolchain acquisition latency drops significantly (extraction overlaps with download)
- Memory usage drops (no need to hold the entire tarball in memory)
- Applies to all tarball downloads: toolchains, registry crates, any future archive fetching

## Considerations

- tar.gz and tar.zst stream naturally (gzip/zstd are streaming decompressors)
- tar.xz also streams (xz is a streaming format despite being slower)
- Error handling: if the download fails mid-stream, partial extraction must be rolled back
- Progress reporting: can report bytes downloaded AND files extracted simultaneously
