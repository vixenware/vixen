# Issue #249: roam v7 migration: avoid ResponseParts.ret.clone() in vx-vfsd hot paths

## Body

## Problem
During roam v7 migration in `vx-vfsd`, several call sites now do `...await?.ret.clone()` to extract payloads from generated client responses.

This reintroduces allocations/copies in paths that were previously effectively zero-copy (or copy-minimal), especially in CAS/VFS read paths.

## Where this currently happens
- `crates/vx-vfsd/src/vfs.rs`
  - `read_chunk_cached()` (`get_chunk(...).await?...ret.clone()`)
  - `get_blobnode_cached()` (`get_node(...).await?...ret.clone()`)
- `crates/vx-vfsd/src/service.rs`
  - `mount_directory_node()` (`get_node(...).await?...ret.clone()`)

## Why this matters
- Inflates memory traffic and latency in VFS/CAS critical path
- Defeats the spirit of roam v7 response zero-copy wrappers
- Risks accidental spread of clone-heavy patterns across codebase

## Follow-up requested
Refactor these internal paths to operate on `SelfRef` / borrowed response bodies directly instead of cloning `ret`.

Potential approaches:
1. Update generated client return ergonomics to expose a non-cloning borrowed accessor path that is pleasant to use in hot loops.
2. Introduce helper APIs in vixen wrappers to consume `ResponseParts` without cloning when only borrowed access is needed.
3. Audit other migrated crates (`vx-store`, `vx-runner`, `vxd`) for similar `.ret.clone()` patterns once their v7 migration lands.

## Acceptance criteria
- No `.ret.clone()` remaining in hot-path CAS/VFS code (`vx-vfsd` at minimum)
- Equivalent behavior tests still pass
- Document expected pattern for future migrations (when clone is acceptable vs when SelfRef/borrowed path is required)
