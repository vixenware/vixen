## Body

Now that CAS v3 stores content-defined chunks, we should compress them. Rust compilation artifacts (rlibs, rmeta, object files) compress extremely well — typically 3-5x with zstd.

### What

- Compress chunks on write with zstd (level 3 or so — fast enough to be free relative to disk I/O)
- Decompress transparently on read
- Store a small header or use a separate metadata field to distinguish compressed vs raw (or just always compress)

### Why

- Disk space: a large workspace can produce gigabytes of artifacts; 3-5x compression is significant
- I/O bandwidth: smaller chunks = faster reads from disk and faster transfers over the network (relevant for remote cache / S3 backend)
- CPU is cheap relative to disk I/O — zstd at low levels is faster than NVMe sequential read

### Considerations

- zstd with a trained dictionary could do even better for similar artifact types, but plain zstd is the right first step
- Chunk-level compression (not blob-level) means deduplication still works — identical chunks still hash the same before compression
- Need to decide: compress-then-hash or hash-then-compress. Hash-then-compress preserves dedup; compress-then-hash doesn't (zstd output can vary across versions). **Hash the raw content, store compressed.**
