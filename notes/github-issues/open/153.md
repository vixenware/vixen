## Body

## Summary

Always unify features across the entire workspace, regardless of which crate is being built. Break Cargo compatibility here intentionally.

## Problem with Cargo's behavior

In Cargo, \`cargo build -p single-crate\` resolves features differently from \`cargo build\` (full workspace). This means:
- Building one crate can succeed, then building the workspace fails (or vice versa)
- Features activate different code paths depending on what you're building
- CI running \`cargo build\` doesn't catch issues that \`cargo build -p foo\` would hit
- The "feature unification problem" is a constant source of bugs

## Vixen's approach: always workspace-wide

- Feature resolution always considers the entire workspace
- \`vx build -p foo\` builds only \`foo\` but resolves features as if building everything
- This means the feature set for any given crate is stable regardless of what you ask to build
- Cache keys are stable: the same crate always gets the same features
- Deterministic: no "works on my machine because I built a different subset"

## Trade-off

This is an intentional Cargo incompatibility. A crate might get features activated that it wouldn't get in a \`cargo build -p\` invocation. This can:
- Increase compile time slightly (more features = more code)
- Expose feature-gated bugs earlier (good)
- Make cache hits more likely (same features every time)

## Implementation

- During feature resolution, always walk the full workspace dependency graph
- Cache the unified feature set per-crate
- When building a subset (\`vx build -p foo\`), use the workspace-unified features but only compile the requested crate and its transitive deps
