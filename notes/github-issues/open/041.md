## Body

## Summary

Build an in-memory directory tree index from `TreeManifest` on first access to enable O(1) path lookups in the VFS layer.

## Motivation

Currently `TreeManifest` is a flat `Vec<TreeEntry>` sorted by path. VFS operations like `readdir()` and path lookups require scanning the entire manifest, which is O(n) where n = number of files.

For large source trees (10k+ files), this becomes a bottleneck, especially for builds that make many small file accesses.

## Proposed Design

1. **Lazy index construction**: On first VFS access to a manifest, build a directory tree structure
2. **Data structure**: Either:
   - `HashMap<PathBuf, TreeEntry>` for O(1) file lookups
   - Trie/radix tree for efficient `readdir()` (list children of a directory)
   - Nested `HashMap<String, DirEntry>` where `DirEntry` is either file metadata or another hashmap

3. **Cache the index**: Keep indexed manifests in an LRU cache keyed by manifest hash

### Example structure
```rust
enum DirNode {
    File { blob: Blake3Hash, size: u64, executable: bool },
    Symlink { target: String },
    Dir { children: HashMap<String, DirNode> },
}

struct IndexedManifest {
    root: DirNode,
}
```

## Benefits

- `readdir("/foo/bar")` → O(1) hashmap lookup instead of O(n) scan
- `stat("/foo/bar/baz.rs")` → O(depth) traversal instead of O(n) scan
- No change to storage format or wire protocol

## Alternatives considered

- **Merkle directories**: Would give similar benefits but requires storage format change. This is a pure runtime optimization that can be added incrementally.
- **Keep flat + binary search**: Manifest is sorted, so could binary search. Still O(log n) and doesn't help `readdir()`.
