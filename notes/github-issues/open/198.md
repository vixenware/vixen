# Issue #198: Same-runner optimization: reuse VFS mount between dependent actions

## Body

## Problem

When action B depends on action A and both are scheduled on the same runner, the current flow is:

```
Action A writes outputs to VFS prefix
  → outputs flushed/ingested into CAS
    → CAS blobs fetched back into VFS for action B's input prefix
      → Action B reads from VFS
```

This is correct but wasteful when A and B are on the same machine. The outputs are right there in the VFS — we uploaded them to the CAS and immediately downloaded them back. The filesystem cache may help, but we're still doing unnecessary CAS round-trips and re-materialization.

## Optimization

When dependent actions are co-located on the same runner, directly reuse action A's output VFS mount as part of action B's input:

```
Action A writes outputs to VFS prefix /actions/A/out/
  → outputs still ingested into CAS (for cache, for remote runners)
  → BUT action B's input VFS includes /actions/A/out/ directly
    → Action B reads from VFS — zero CAS round-trip for A's outputs
```

The bytes never leave the machine. The VFS already has them materialized (possibly still in the page cache). Action B gets them at memory speed.

## Design considerations

### CAS ingestion still happens
The outputs must still go to CAS for:
- Cache hits on future builds
- Distribution to other runners
- Persistence

But ingestion can happen **in parallel** with action B starting — it's not on the critical path.

### Distributed scheduling
When A and B are on different runners, the current flow is correct — B must fetch from CAS. This optimization only applies when the scheduler co-locates dependent actions.

This means the scheduler has an incentive to co-locate dependent actions on the same runner when possible. The scheduler should prefer:
```
Runner 1: A → B → C (dependency chain, reuse mounts)
Runner 2: D → E → F (independent chain)
```
over:
```
Runner 1: A, D (unrelated)
Runner 2: B, E (B needs A's output from CAS)
```

### VFS lifetime management
Action A's VFS prefix must stay alive until all dependent actions on the same runner have consumed it. Reference counting or explicit "I'm done with A's outputs" signals from the scheduler.

### Interaction with sandbox
The sandbox must allow action B to read action A's output prefix. This is a read-only mount — B cannot write to A's output directory.
