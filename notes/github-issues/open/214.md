## Body

## Summary

This issue defines the **epic vision** for moving build planning in vixen from hardcoded Rust orchestration to a deterministic, interpreted **EDN/Clojure-subset rule system**.

The goal is not "a tiny POC rule script". The goal is:

- vixen core becomes a small, auditable, deterministic execution kernel
- language support (starting with Rust) is implemented as a versioned rule pack
- dynamic build behavior (discovered inputs, generated outputs, dynamic deps) is first-class and explainable
- the resulting graph remains cache-correct, reproducible, and fast

This epic supersedes the exploratory framing in #150 and turns it into an execution-ready program of work.

## Why This Matters

Today, most build orchestration policy is embedded in Rust code paths. That works for initial velocity, but it couples:

- policy and mechanism
- language semantics and executor internals
- experimentation and daemon release cadence

That coupling raises the cost of:

- adding new rule semantics
- supporting new languages and toolchains
- introspecting why graph shape changed
- validating correctness of dynamic behavior over time

We want a world where changing build semantics is often a **rule bundle update**, not a daemon rewrite.

## Product Vision

### vixen as a deterministic build kernel

The kernel owns:

- CAS and manifests
- sandboxed action execution
- scheduler / concurrency / cancellation
- validity checks, contracts, and invariants
- observability + provenance plumbing

Rules own:

- graph topology
- edge semantics
- dynamic graph expansion policy
- language-specific planning logic (Rust first)

### Pure planning contract

Planning is a pure function of:

- workspace snapshot(s)
- lockfiles / registries metadata
- toolchain manifests
- explicit build options
- rule bundle content hash + declared config

No hidden reads. No time-based behavior. No process-global randomness. No ambient host state.

### Fixed-point dynamic planning

Planning runs until stable:

1. rules emit actions/edges
2. some actions run and emit structured facts (dyndeps, dynout, diagnostics)
3. planner re-evaluates with the new facts
4. graph grows monotonically and deduplicates by identity
5. stop when no new nodes/edges/facts appear

This is how we support build scripts and generated sources **without** giving up determinism.

## Language Model (EDN/Clojure subset)

Assumption for this epic: parser/interpreter/runtime host already exist.

### Allowed properties

- data-first forms: maps, vectors, sets, keywords, strings, numbers, booleans
- deterministic control flow over finite collections
- bounded recursion/iteration only (or no recursion; either is fine if bounded and analyzable)
- no wall clock, RNG, network, host filesystem, process APIs
- no unbounded loops

### Required builtins (conceptual)

- graph emission: `emit-action`, `emit-edge`, `emit-group`
- fact emission: `emit-fact`
- rule queries: `facts`, `artifacts`, `actions`, `workspace-units`
- deterministic transforms: `sort`, `group-by`, `join`, `mapcat`, etc.
- domain adapters (kernel-provided):
  - `read-cargo-manifest`
  - `read-cargo-lock`
  - `parse-depinfo`
  - `parse-build-script-lines`
  - `target-normalize`

All adapters are pure against declared inputs and produce canonical, typed outputs.

## Graph & Edge Semantics

### Node kinds

- `action`
- `artifact`
- `fact`
- `group`

### Edge kinds

- `ifchanged` (re-run dependent if dependency content changed)
- `ifwritten` (edge based on produced output existence/content)
- `ifcreate` (trigger on first creation)
- `ifdeleted` (trigger on deletion)
- `always` (ordering-only / unconditional dependency)

### Dynamic structures

- `dyndeps`: discovered dependencies emitted by action outputs
- `dynout`: discovered outputs emitted by action outputs

These are not string hacks; they are typed records with provenance.

## Rust Coverage Vision (How much can be expressed?)

Short answer: **almost all planning/orchestration logic** for Rust.

### Expressible in rules

- workspace crate/unit discovery
- target/unit expansion (lib/bin/test/bench/doc if desired)
- feature unification policy
- host-vs-target split planning
- registry acquisition policy and checksum constraints
- toolchain acquisition/finalization policy
- compile action emission + dependency wiring
- build script pipeline:
  - compile `build.rs`
  - execute build script action
  - parse `cargo:` directives into facts
  - emit rerun edges and generated-input edges
- proc-macro lane and downstream macro consumer wiring
- depfile-driven dynamic dependency updates
- dynamic source generation and follow-up compile/link actions
- link/materialization policy for final artifacts

### Must remain in kernel primitives

- actual process execution and sandboxing
- CAS access, blob/tree/manifest operations
- scheduler and concurrency controls
- trust boundaries, validation, quotas, and safety checks
- canonical hashing and cache publish/lookup

## Example: Rule Sketches

### Rule: emit compile unit actions

```clojure
(defn plan-rust-units [ctx]
  (let [units (workspace-units ctx :rust)
        tc    (ensure-rust-toolchain ctx)
        cfg   (build-config ctx)]
    (doseq [u (sort-by :unit-id units)]
      (emit-action
        {:id   [:rust/compile (:unit-id u)]
         :kind :rust.compile
         :in   {:unit u :toolchain tc :config cfg}
         :out  {:manifest [:artifact [:rust/output (:unit-id u)]]}}))))
```

### Rule: build script dynamic expansion

```clojure
(defn expand-build-script-results [ctx]
  (doseq [r (facts ctx :kind :rust.build-script/result)]
    (doseq [p (:rerun-if-changed r)]
      (emit-edge {:from (:owner-action r)
                  :to   [:artifact [:workspace/path p]]
                  :kind :ifchanged}))
    (doseq [g (:generated-files r)]
      (emit-fact {:kind :rust.generated/source
                  :unit (:unit r)
                  :path g
                  :via  (:owner-action r)}))))
```

### Rule: generated source triggers follow-up compile actions

```clojure
(defn plan-generated-source-compiles [ctx]
  (doseq [f (facts ctx :kind :rust.generated/source)]
    (emit-action
      {:id   [:rust/compile-generated (:unit f) (:path f)]
       :kind :rust.compile.generated
       :in   {:unit (:unit f) :src (:path f)}
       :out  {:manifest [:artifact [:rust/generated-output (:unit f) (:path f)]]}})))
```

The point is not this exact syntax. The point is that dynamic graph growth is first-class, typed, deterministic, and explainable.

## Determinism & Safety Contract

### Hard constraints

- no clock/time API
- no randomness
- no ambient FS access
- no network calls
- no shelling out from rule code
- canonical ordering for all emitted collections
- stable serialization for all facts/actions

### Termination controls

- monotonic data domains
- action identity deduplication
- max fixed-point iterations (guardrail)
- planner fuel / budget accounting
- hard error with full provenance when guardrails trip

### Reproducibility property

Given identical declared inputs and rule bundle hash, planner output graph and cache keys are identical.

## Cache Correctness Model

For each action, key derivation includes:

- action kind + normalized parameters
- transitive input artifact manifests (or equivalent closure summary)
- selected toolchain IDs/manifests
- relevant discovered facts (e.g. rerun env deps)
- rule bundle hash + rule ABI version

Any change in semantics-driving data invalidates exactly the right actions.

## Explainability & UX

We should be able to answer:

- Why was this action created?
- Which rule emitted it?
- Which facts triggered dynamic expansion?
- Why did this node re-run?
- Which edge kind caused invalidation?

Expected output surfaces:

- build report includes planner provenance (rule id, binding summary, fact ids)
- `vx build --explain` can render dynamic expansion timeline
- graph serialization captures edge kinds and provenance metadata

## Architecture Boundary (Proposed)

### Rule planner pipeline

1. Load rule bundle + verify ABI/version
2. Seed initial facts from workspace/toolchain metadata
3. Evaluate planner pass
4. Execute ready actions as required for discovery stages
5. Ingest action-produced facts
6. Repeat until fixed point
7. Lower to final execution DAG (or continue interleaved planning/execution model)

### Compatibility layer

- existing `ActionGraph` / executor remain valid during transition
- rule planner lowers to existing action types first
- new action kinds can be introduced behind feature gates

## Migration Plan (Epic-level)

1. Introduce typed intermediate representation (`RulePlan`) with provenance and edge kinds.
2. Build deterministic rule host adapter and builtin API surface.
3. Implement Rust rule pack parity path with existing planner.
4. Run dual-planner mode (legacy + rule planner) and diff results.
5. Switch default to rule planner when parity + perf + correctness criteria are met.
6. Remove legacy hardcoded planner path after bake-in.

## Success Criteria

### Correctness

- Graph parity against legacy planner for supported Rust cases
- Stable cache behavior under repeated identical builds
- Deterministic planner outputs across machines

### Capability

- Build script-driven dynamic deps handled through typed facts
- Generated sources and dynamic outputs supported without ad hoc executor logic
- Proc-macro and host-target split fully represented in rules

### Performance

- Planner overhead acceptable for medium/large workspaces
- fixed-point iterations bounded and observable
- no regressions in incremental no-op builds beyond agreed threshold

### Operability

- provenance-rich explain output
- actionable failure messages for rule errors and guardrail violations
- metrics for planner passes, emitted nodes, iteration count, dedup rates

## Risks & Mitigations

- Risk: dynamic expansion causes runaway growth
  - Mitigation: monotonic domains, identity dedup, iteration caps, debug counters
- Risk: rule API becomes too powerful and leaks nondeterminism
  - Mitigation: strict builtin whitelist and host capability model
- Risk: parity drift with legacy planner
  - Mitigation: dual-planner diff tests and CI fixtures
- Risk: planner performance overhead
  - Mitigation: incremental memoization and canonical data representations

## Out of Scope (for this epic)

- Arbitrary user-defined foreign function hooks in planner
- Non-deterministic rule APIs
- Supporting every Cargo edge case on day one
- Immediate removal of legacy planner before parity and diagnostics are solid
