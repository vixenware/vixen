## Summary

This epic tracks building the **Vixen language** (the rule language for vixen) as a first-class language platform, not just an embedded config syntax.

Goal: deliver a language ecosystem with best-in-class developer experience:

- clear language specification and determinism contract
- robust parser + interpreter/runtime conformance
- CLI tooling (`fmt`, `lint`, `check`, test harness)
- great editor support (LSP, syntax highlighting, diagnostics, code actions)
- easy cross-repo implementation while preserving vixen integration quality

## Vision

Vixen language should feel like a real language, not a one-off internal DSL.

Ideal user experience:

1. Open a `.vx` file and immediately get syntax highlighting, errors, and completions.
2. Rename symbols safely and get go-to-definition/find-references.
3. Format and lint rules with deterministic output and actionable diagnostics.
4. Run `vxl check` and get semantic validation before invoking a build.
5. Run `vx build --explain` and map planner behavior directly back to rule locations.

## Outcomes

- deterministic semantics and host capability boundaries are formally documented
- rule authors have fast feedback loops locally and in CI
- editor support quality matches modern language expectations
- implementation can be split across repositories without losing coherence

## Scope

- language-level design and developer tooling standards
- editor and LSP experience goals and validation criteria
- cross-repo coordination model for implementation and release

## Non-goals

- forcing all implementation to live in the vixen repository
- shipping every IDE on day one
- sacrificing determinism or safety for convenience APIs

## Success Criteria

- Vixen language spec and conformance suite exist and are versioned
- LSP provides stable completion/diagnostics/definitions on real rule code
- formatter and linter are reliable and CI-friendly
- vixen integration exposes provenance-rich rule diagnostics and explainability
