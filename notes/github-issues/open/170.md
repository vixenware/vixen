## Body

## Summary

Integrate with cargo-nextest as the test runner, not just compile code but run tests through vixen.

## Why nextest

- Per-test process isolation (catches shared state bugs)
- Better output: test list, progress, retries, JUnit XML
- Faster: parallel execution with better scheduling
- Machine-readable output for CI

## Scope

### vx test

- `vx test` runs all tests in the workspace
- `vx test -p foo` runs tests for a specific crate
- `vx test -- --filter name` passes filters through

### Integration points

- Compile test binaries using vixen's build graph (--test target type)
- Hand off to nextest for execution (or embed nextest's runner logic)
- Collect structured test results (pass/fail/ignore/flaky per test)
- Feed results back to TUI with progress
- Machine-readable output (JUnit XML, JSON) for CI

### Compilation changes needed

- Support `--test` crate type (test harness binaries)
- Support `#[cfg(test)]` compilation (compile crate twice: once as lib, once as test)
- dev-dependencies: resolve and compile deps only needed for tests
- Integration tests: compile files in `tests/` directory as separate test binaries

### Open questions

- Do we shell out to `cargo nextest run` with our compiled binaries, or embed the runner?
- How does the sandbox interact with test execution? Tests may need network, temp dirs, etc.
- Should test results be cached? (Cargo doesn't, but with content-addressed inputs we could)
