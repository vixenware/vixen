# Issue #195: VFS output files are memory-only: spill large artifacts to disk

## Body

## Problem

On Linux (FUSE) and macOS (FSKit), files written by actions (rustc output: .rlib, .rmeta, binaries, etc.) are held entirely in memory until the action completes and outputs are ingested into the CAS. For small artifacts this is fine, but:

- A release-mode binary can be 50-100+ MB
- .rlib files for large crates can be 10-20 MB
- Multiple actions running in parallel multiply this
- A parallel build with 8 actions writing large outputs can hold hundreds of MB in RAM just for VFS output buffers

This is a silent memory pressure problem that gets worse as builds get larger.

## Fix

Two-tier write path for VFS output files:

1. **Small files** (under a threshold, e.g., 1 MB): keep in memory as today — fast, simple
2. **Large files** (over threshold): spill to a temporary file on disk, then ingest into CAS from disk

The threshold should be tunable. The spill should be transparent to the action — it still writes to the VFS path, the VFS backend decides where the bytes go.

### Implementation

- Track written bytes per file handle
- When a file crosses the threshold, flush the memory buffer to a temp file and switch to file-backed mode
- On close/sync, ingest from disk instead of memory
- Clean up temp files after ingestion
