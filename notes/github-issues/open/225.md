## Summary

Define the **ideal Vixen language developer experience** end-to-end.

This issue is the product contract for what "best-of-class" feels like when authoring rules.

## North-Star Experience

1. First-file experience
- Open a `.vx` file and instantly get syntax highlighting, semantic diagnostics, and hover docs.

2. Editing ergonomics
- completions for builtins, keywords, symbols
- go-to-definition / find references / rename
- signature help and inline docs
- code actions for common fixes

3. Fast feedback
- `vxl check` for static and semantic validation
- diagnostics mapped to source spans and rule provenance
- deterministic formatter (`vxl fmt`) with stable output

4. Debuggability
- planner trace/explain views that map actions/facts back to rule sites
- readable errors for capability violations and determinism guardrails

5. Team workflows
- CI-friendly lint/check/fmt commands
- stable machine-readable diagnostics for review tooling
- compatibility checks for language/runtime/ABI versions

## Deliverable

A detailed UX/design spec with user journeys and acceptance criteria that child implementation issues can follow (including work done outside this repo).

## Acceptance Criteria

- North-star UX doc is committed and reviewed
- Includes command UX (`fmt`, `lint`, `check`, explain)
- Includes LSP capability matrix and quality bars
- Includes rollout phases (minimum useful -> great -> best-in-class)

## Notes

This is intentionally an experience spec, not an implementation task.
