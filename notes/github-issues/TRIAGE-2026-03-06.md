# Triage Notes - 2026-03-06

This note was written after exporting and reading all open GitHub issues into
`notes/github-issues/open/`.

## Current view

A blanket "close everything and restart" would lose too much useful
specification work.

The backlog is noisy, but a lot of the Cargo/Rust issues are not just
"implement this in Rust" chores. Many of them are:

- acceptance criteria for a future Rust rule pack
- semantic decisions that still need to exist even if planning moves into a
  language
- integration tests that will be needed to prove parity during migration

The cleaner move is:

1. keep the kernel/platform floor issues open
2. keep the language/planner issues open
3. group the Cargo-specific issues under a new "Rust rule-pack parity" track
4. close or defer only the issues that are mostly implementation cleanup,
   polish, or no longer on the critical path

## Missing work implied by the pivot

After reading the issue bodies, the biggest gap is that the new direction still
needs a few sharper child issues spun out of `#214`:

- `RulePlan` IR schema and provenance model
- planner host ABI/versioning
- parser/interpreter host integration
- edge-kind support end-to-end in reports
- Rust rule-pack parity epic that absorbs the current Cargo-compat cluster

Without those, closing the old Rust issues would create a roadmap hole.

## Bottom line

The pivot looks real and is already reflected in the better issues.

I would not close all issues. I would:

1. create a `Rust rule-pack parity` epic
2. move or relabel the Cargo-specific issues under that epic
3. keep kernel/platform and language issues open
4. close only the cleanup/polish issues that no longer support the new plan
