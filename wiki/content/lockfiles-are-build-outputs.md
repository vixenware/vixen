## Context

A `Cargo.lock` (and any Vixen-side lockfile) is conceptually awkward: it lives next to `Cargo.toml` in the repo, is regenerated by the build, gets checked in, and changes when dependencies change. It looks like a file the build *mutates*.

That framing doesn't fit the Vixen evaluation model, which treats every node as `inputs → operation → outputs`. A mutation-of-input has no clean cache story.

## Decision

Lockfiles are **build outputs**, not mutations of inputs. The resolution operation is a build-graph node:

```
(Cargo.toml, registry view, resolver-version) → solve → Cargo.lock
```

The fact that the output lands at the same on-disk path as a previous lockfile is a **file-system convention**, not a semantic mutation. The build graph treats the new lockfile as a freshly-produced artifact whose inputs are the toml, the registry state at that moment, and the resolver code.

## Consequences

- **Caching works uniformly.** Resolution is cached by its inputs. Same `Cargo.toml` + same registry view (no new published versions since last resolve) + same resolver = same `Cargo.lock` = instant. New version published → different registry view → cache miss → re-resolve. The cache decides; no bespoke "is this lockfile stale" heuristic.
- **`cargo update` is "force re-resolution against current registry state."** Not magic. Just a way of asking the user "evaluate the resolver node against today's registry, ignore any prior lockfile-as-output." The result is a new lockfile output.
- **Lockfiles cross-target cleanly.** A workspace targeting linux-x86_64 and one targeting macos-arm64 resolve to potentially different lockfiles. That's two outputs of two resolution operations, both cached, both reproducible. Cargo's existing per-target lockfile machinery is the same shape; we just inherit it.
- **No surprises around "the build modified my checked-in lockfile."** The build wrote a freshly-derived artifact to the conventional path. If the customer's git working tree shows a diff, that's because the inputs (registry state, resolver version) changed since the lockfile was checked in. The diff is honest.
- **Domain-package version pins fit the same model.** A workspace also depends on specific versions of Vixen packages (`vixen-rust@2.4.1`, `vixen-c@1.8.0`). Those pins are inputs to the resolution operation, and they appear in the lockfile output. See [[Package management for Vixen]].
