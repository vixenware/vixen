# Rodin churn taxonomy

Generated by `cargo run -p rodin-survey --bin rodin-churn-taxonomy`. Classifies every REAL block-break identified by `rodin-block-forensics` (see `docs/design/rodin-block-forensics.md`) by change kind: requirement widening/narrowing/incompatible-bump, dependency add/remove (optional or not), feature-map co-occurrence, and how many distinct dependency edges a break actually touches.

## Method

- A REAL break is one where the fixed-target runtime signature (deps minus dev/false-target, plus merged features/features2) differs AND the narrower Round-10 edge-read-set (actual/req/optional per non-dev/true-target dep) also differs — i.e. exactly the REAL CHURN rows from the forensics pass.
- Requirement changes are classified by sampling a probe set of versions (every version-like token in either requirement string, perturbed by +-1 at each semver component, plus 0.0.0/9999.0.0 sentinels) and comparing which probes each requirement string accepts via `semver::VersionReq::matches`. This is a **sampling approximation**: dense enough to separate every case observed in this dataset, but not a proof of interval containment.
  - **req-widened**: every probe the old requirement accepted, the new one also accepts, plus at least one more.
  - **req-narrowed**: the reverse — new accepts a strict subset of what old accepted.
  - **req-bumped-incompatibly**: neither accepts a subset of the other (some probes flip both ways) — the classic `^1 -> ^2` shape.
  - **req-reshaped**: the two requirement strings accept the exact same probe set (e.g. `^0.6.3 -> ~0.6.3` for a 0.x version, or `^1.4.0 -> >=1.4.0, <2.0.0`) — syntax changed, resolver-visible set did not.
- A break's *touched edges* is the set of dependency names it adds, removes, or req-changes. Feature-map-only co-occurrence is tracked separately and does not count as touching an edge.

## Edge locality

`single-edge` = fraction of REAL breaks that touch exactly one dependency name (add/remove/req-change). `avg edges/break` = mean distinct edges touched. `corrected blocks` and `edge-read blocks` reproduce the forensics-pass counts (whole fixed-target row vs Round-10 edge-read-set); `blocks ratio` = corrected/edge-read, i.e. how many whole-row blocks collapse into one edge-read-set block on average — this stays close to 1.0 because narrowing the *field set* barely helps when almost every version touches *some* edge's req.

### Per-edge stability vs whole-row stability — the key ratio

For every dependency name that ever appears, `edge versions/block` counts how many consecutive versions THAT ONE edge's own (req, features, optional, default_features, target) state holds steady before it changes, averaged over every edge. `whole-row versions/block` is `non-yanked versions / corrected blocks` from the forensics pass — how long the *entire manifest* stays stable. `fineness` = edge/whole-row, i.e. how much longer a single edge's fact would remain valid under per-edge tracking than it does today under whole-row blocking.

## Discussion

### async-graphql: what is it actually doing

async-graphql was the block-forensics STOP (missing cached row); with its sparse-index row fetched and cached (see `crates/rodin-survey/fixtures/sparse-index/async-graphql.jsonl`), it classifies as 347 real breaks over 440 non-yanked versions — confirming the "350 blocks, worst case" figure from the forensics pass (349 corrected blocks here). Two things drive it, both visible in the per-crate table above:


1. **Workspace-split lockstep pins.** async-graphql is split into sibling crates (`async-graphql-derive`, `async-graphql-parser`, `async-graphql-value`) that are version-pinned from the main crate, usually with an exact or tight caret req that gets bumped on *every* release of the main crate, whether or not anything relevant to the dependent changed. This is why async-graphql's avg-edges/break (2.75) and single-edge ratio (0.375) are the outliers in the dataset — most other investigated crates (serde: 1.00 single-edge every time; openssl: 1.25 avg edges) have at most one or two such external pins (e.g. openssl/openssl-sys, clap/clap_derive-clap_builder). async-graphql simply has more of them, plus more that changed simultaneously.
2. **Continuous optional-integration churn.** async-graphql accumulates and drops *optional*, feature-gated integrations with the wider ecosystem (chrono, chrono-tz, bson, uuid, url, im, parking_lot, tempfile, and others) as it adds/removes support for external types across its lifetime. These show up as dep-added/dep-removed pairs, frequently marked optional, often co-occurring with a features/features2 map change (the crate is wiring a new dep into a new optional feature in the same release). A `graphql-parser` -> `async-graphql-parser` swap (1.10.12 -> 1.11.0, `async-graphql-parser: added` + `graphql-parser: removed` in the same version) is a rename disguised as add+remove — a real break, not an artifact, since any fact keyed to the old edge name is genuinely gone.

Both are genuine, unavoidable churn under any read-set narrowing that still tracks whole-row (or even whole-row-with-narrowed-fields) state: as long as blocking is done per row, one lockstep-pinned sibling or one new optional integration anywhere in the manifest re-shatters the block for every other, unrelated edge too.

### Monotone-compatible changes: think carefully, not just "real churn happened"

A CDCL-style solver over version regions learns facts of the shape *"these regions are jointly UNSAT"* — a conflict clause. The question this taxonomy exists to answer is: which of the REAL-CHURN field changes above are guaranteed to leave a previously-learned conflict clause valid for the OLD version, and which can silently invalidate it?

Treat a manifest as a constraint set over the resolver's boolean variables (one clause per dependency edge: "if this crate-version is chosen, this dependency's requirement must hold"). UNSAT-ness is **monotone under adding constraints**: if a constraint set `S` is unsatisfiable, any superset `S' ⊇ S` is unsatisfiable too — new constraints can only narrow the solution space, never widen it back open. That gives a real, sound asymmetry:

- **dep-added** adds a brand-new constraint edge. It can never invalidate a conflict clause that was already provable from the OLD, smaller constraint set — that clause used a subset of what's now available and remains sound. It can, and often does, introduce *new* conflicts the old version never had (this dataset counts 194 dep-added instances), but those are additive, not retroactive.
- **req-narrowed** shrinks the accepted-version interval for an existing edge — also constraint-tightening (fewer satisfying assignments). Same argument: a conflict clause proved when the requirement was looser remains provable when it's stricter. This dataset's dominant req-change kind (708 of ~1450 req-change instances, mostly ordinary patch/point releases: `^0.8.0 -> ^0.8.1` is a narrowing under caret semantics, not a "bump", because it raises the floor without moving the ceiling) is therefore monotone-safe far more often than the raw REAL-CHURN count suggests.
- **dep-removed** deletes a constraint edge. If a conflict clause depended on that edge (e.g. "crate X requires Y, and Y<2 conflicts with Z"), removing the edge can make the clause's premise vanish — the clause is no longer *derivable* from the new manifest, even though nothing else proves it false either. This is not the same as "the fact becomes wrong"; it means the fact's derivation is no longer licensed and must be re-checked. 94 required + 49 optional dep-removed instances in this dataset are candidates for this asymmetry.
- **req-widened** and **req-bumped-incompatibly** relax or shift the accepted interval — the dangerous direction. A version combination that was UNSAT under the old (tighter or differently-shaped) requirement can become SAT under the new one. Any conflict clause resting on that edge must be treated as invalidated, full stop; the sampling method above found only 28 unambiguous widenings but 709 incompatible-bump instances (interval *shifts*, e.g. `^0.5.0 -> ^0.6.0`), which are widenings-with-narrowing-elsewhere and must be treated as unsafe on the SAT side even though they also drop old floor versions.

Net: roughly the constraint-*tightening* moves (dep-added, req-narrowed) are safe to treat as extending a fact's validity range without re-derivation; constraint-*loosening* moves (dep-removed, req-widened, req-bumped-incompatibly) are not. Today's implementation draws the validity boundary at "the read-set changed at all", which is strictly more conservative than this — it also invalidates on every dep-added and req-narrowed instance, i.e. on the majority-safe direction. That gap, quantified per-crate above as the edge/whole-row fineness ratio (aggregate 7.29x), is the target for Part 2's research question.
